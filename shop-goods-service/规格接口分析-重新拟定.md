# 规格管理接口分析

本分析依据当前 goods 模块、`shop-api` 中的实体与分页对象、`shop-common` 中的 `Result`，以及仓库的 `shop.sql` 编写。它是重新实现时的设计建议，不代表这些接口已经完成，也未核对运行中的数据库。

## 1. 功能范围与业务约定

规格管理维护“规格 + 规格选项”这一组数据。例如，规格是“尺码”，选项是“165、170、175”。本次先完成分页条件查询、新增、详情回显、修改、单条删除五个接口。批量删除、模板下拉列表、商品 SKU 生成不在本次基础实现范围内。

以下是本分析采用的约定，属于建议，后续可以根据实际页面需求调整：

- 新增和修改均提交规格名称与完整的选项列表，一个接口完成整组保存。
- 修改时保留已有选项 ID，通过 ID 区分新增、更新和删除。
- 允许规格没有选项：空数组 `[]` 合法；缺少选项字段或传 `null` 不合法，避免误删。
- `orders` 必填，为大于或等于 0 的整数，数值越小越靠前；相同排序值允许，按选项 ID 升序作为第二排序条件。
- 名称保存前去除首尾空白；同一个规格下不允许出现完全相同的选项名称。这里按去除空白后的文本相等判断，不额外设计大小写折叠规则。
- 暂不要求不同规格的名称全局唯一。当前建表脚本没有名称唯一约束，不把全局唯一当作已存在的规则。
- 删除不存在的规格返回“规格不存在”；不把未删除任何记录当作删除成功。
- 当前表结构没有版本字段，修改按最后一次成功保存的完整表单生效。如将来需要防止多人编辑覆盖，再单独设计版本控制。

## 2. 数据关系

实际表名是 `tb_specification` 和 `tb_specification_option`，原分析中的 `tb_spec`、`tb_spec_option` 是简写，写 SQL 时使用实际表名。

### 2.1 规格表 `tb_specification`

| 数据库字段 | Java / JSON 字段 | 含义 |
| --- | --- | --- |
| id | id | 规格主键，自增 |
| spec_name | specName | 规格名称，最多 255 个字符 |

### 2.2 选项表 `tb_specification_option`

| 数据库字段 | Java / JSON 字段 | 含义 |
| --- | --- | --- |
| id | id | 选项主键，自增 |
| option_name | optionName | 选项名称，最多 200 个字符 |
| spec_id | specId | 所属规格 ID |
| orders | orders | 排序值 |

一条规格对应零到多条选项，关联条件为 `tb_specification.id = tb_specification_option.spec_id`。仓库建表脚本没有声明外键，因此不能依赖数据库自动检查关联或级联删除。

`specificationOption` 是当前实体中的集合字段，不是规格主表里的数据库列。为了减少重写时的额外调整，本分析沿用这个 JSON 字段名。

## 3. 请求与返回对象

对象按用途区分即可，不必为每个接口创建一套重复字段。

| 用途 | 建议对象 / 内容 |
| --- | --- |
| 分页条件 | `PageQueryParams<SpecificationQueryDTO>`，查询条件只包含 `specName` |
| 新增、修改表单 | 共用 `SpecificationSaveDTO`：`id`、`specName`、`specificationOption` |
| 表单中的选项 | `SpecificationOptionSaveDTO`：`id`、`optionName`、`orders` |
| 分页结果中的一行 | 现有 `SpecificationVo`：`id`、`specName` |
| 详情回显 | `SpecificationDetailVO`：`id`、`specName`、`specificationOption` |

上面的 DTO 与详情 VO 是建议新增的对象，不是项目当前已经具备的类。也可以先复用当前 `Specification` 完成学习实现，但 Controller 不应把前端提交的 `specId` 直接交给数据库。

保存请求不需要 `specId`，所属规格由后端确定。选项响应可以复用现有 `SpecificationOptionVo`，包含 `id`、`optionName`、`specId`、`orders`。

所有响应沿用 `Result<T>`：成功业务码为 `200`，字段为 `code`、`message`、`data`。错误建议采用 `400`（参数非法）、`404`（规格不存在）、`409`（关联数据阻止操作）、`500`（内部异常）。这些是响应体中的业务码；HTTP 状态码应由 Controller 或异常处理统一约定，不能认为设置 `Result.code` 就自动改变 HTTP 状态。

## 4. 接口总览

路径沿用现有品牌 Controller 的命名风格，统一前缀建议为 `/specification`。

| 功能 | 方法 | 路径 | 成功 data |
| --- | --- | --- | --- |
| 分页条件查询 | POST | `/specification/queryPage` | `PageList<SpecificationVo>` |
| 新增 | POST | `/specification/add` | 新生成的规格 ID |
| 详情回显 | GET | `/specification/detail/{id}` | 规格及完整选项列表 |
| 修改 | POST | `/specification/update` | `null` |
| 删除 | DELETE | `/specification/delete/{id}` | `null` |

这些是拟定路径，当前项目尚未提供规格 Controller。后续通过网关调试时，还需要核对网关是否转发 `/specification/**`。

## 5. 分页与条件查询

请求示例：

```json
{
  "pageNum": 1,
  "pageSize": 10,
  "params": {
    "specName": "尺码"
  }
}
```

响应示例：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "total": 1,
    "rows": [{ "id": 26, "specName": "尺码" }]
  }
}
```

处理步骤：

1. 校验 `pageNum >= 1`、`1 <= pageSize <= 100`。100 是本分析建议的分页上限；当前分页对象的默认值为 0，不能把漏传参数直接当作合法分页。
2. `params` 缺少或为 `null` 时按无条件查询处理；名称为空或去除空白后为空时不增加名称条件。
3. 使用名称包含查询；本分析将 `%`、`_` 视为普通搜索字符，写查询时需要处理 LIKE 的通配符转义。
4. 在执行规格主表查询前设置分页，主表按 `id DESC` 固定排序。
5. 从原始分页查询结果取得 `total`，再转换成 `SpecificationVo`，返回 `total + rows`。

列表只查询规格主表，不查询选项。不直接把一对多联表结果分页，否则一条规格可能占多行，使总数和页大小失真。查不到数据时返回 `total: 0`、`rows: []`；超出末页时，`rows` 为空，`total` 仍是符合条件的总条数。

## 6. 新增规格及选项

请求示例：

```json
{
  "specName": "颜色",
  "specificationOption": [
    { "optionName": "黑色", "orders": 1 },
    { "optionName": "白色", "orders": 2 }
  ]
}
```

成功响应示例：

```json
{ "code": 200, "message": "操作成功", "data": 34 }
```

这里的 34 只是示例，以数据库实际生成的 ID 为准。

处理步骤：

1. 校验规格名称非空、长度不超过 255；选项列表不能为 `null`，元素不能为 `null`。
2. 校验每个选项的名称非空、长度不超过 200，排序值符合约定，同规格选项名不能重复。
3. 新增请求的规格 ID、选项 ID 必须缺省或为 `null`；不允许调用方指定已有主键。
4. 插入规格主表，并把数据库生成的 ID 回填到后端实体。
5. 将每条选项的 `specId` 设置为新规格 ID，再插入选项表。原分析的“再添加 tb_spec”应为“再添加规格选项”。
6. 选项列表为空时跳过选项插入，避免生成没有 VALUES 内容的 SQL。
7. 返回新规格 ID，方便随后查询详情。

事务边界：整个新增 Service 方法开启事务。主表成功、选项失败时，主表插入也必须回滚，不能留下半组数据。建议写方法统一明确异常回滚规则，例如 `@Transactional(rollbackFor = Exception.class)`，且不要吞掉异常后返回成功。

本次新增接口只要求返回规格 ID，无需依赖选项批量插入后的逐项 ID 回填；选项 ID 可通过详情接口获取。

## 7. 详情查询与编辑回显

请求示例：`GET /specification/detail/26`。

响应示例：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "id": 26,
    "specName": "尺码",
    "specificationOption": [
      { "id": 91, "optionName": "165", "specId": 26, "orders": 1 },
      { "id": 92, "optionName": "170", "specId": 26, "orders": 2 }
    ]
  }
}
```

处理步骤：

1. 校验 ID 为正整数，按 ID 查询规格主表；不存在时返回“规格不存在”。
2. 按 `spec_id` 查询这个规格的全部选项，按 `orders ASC, id ASC` 排序。
3. 组装一个详情对象返回，选项不存在时返回 `[]`。

当前主表的 `selectByPrimaryKey` 只查询 `id`、`spec_name`，不会因为实体里声明了集合字段就自动加载选项。建议使用两次简单查询后组装，不必为单条详情增加复杂联表映射。

页面删除选项行时，只从本地表单移除；点击“保存”后，再通过修改接口持久化。

## 8. 修改规格及选项

修改接口采用完整表单保存，不能把它理解为“只更新传入的非空字段”。

假设数据库中规格 26 的选项有 91、92、93，提交如下表单：

```json
{
  "id": 26,
  "specName": "尺码",
  "specificationOption": [
    { "id": 91, "optionName": "165", "orders": 1 },
    { "id": 92, "optionName": "170（标准）", "orders": 2 },
    { "optionName": "180", "orders": 3 }
  ]
}
```

保存后：91 保留，92 修改，93 删除，“180”新增并获得新 ID。已有选项 ID 保持不变。

### 8.1 用 ID 判断三类操作

| 提交情况 | 后端动作 |
| --- | --- |
| 选项没有 ID 或 ID 为 `null` | 新增，`specId` 使用当前规格 ID |
| 选项有 ID，且属于当前规格 | 更新名称和排序 |
| 数据库中属于当前规格的选项 ID 未出现在提交列表中 | 删除该选项 |
| ID 不存在，或属于其他规格 | 拒绝整次修改 |
| 同一个选项 ID 在请求中出现多次 | 拒绝整次修改 |

ID 为 0、负数不能当作新增标记，新增应使用缺省或 `null`。

### 8.2 Service 处理顺序

1. 校验规格 ID、名称、完整选项列表以及各选项字段。
2. 查询规格是否存在；不存在则结束并返回错误。
3. 查询当前规格的全部旧选项，记录旧 ID 集合。
4. 校验请求中所有非空选项 ID 都在旧 ID 集合中，且不重复。先完成全部校验，再执行写入。
5. 计算待删除 ID：旧 ID 集合减去本次提交的已有 ID 集合。
6. 更新规格名称。
7. 删除待删除选项；更新保留选项的名称和排序；插入没有 ID 的新选项。三个集合为空时分别跳过对应操作。
8. 返回成功，页面重新查询详情获取新选项 ID。

选项更新和删除建议同时使用 `id` 与当前 `spec_id` 作为条件，防止操作到其他规格的选项。更新已有选项时不修改 `spec_id`，不能允许通过表单把选项转移到其他规格。

整个修改 Service 方法必须开启事务。任意一步失败，规格名称与选项变化一起回滚。不要仅凭 UPDATE 影响行数为 0 判断记录不存在，提交与原值相同的数据也应允许成功；存在性由前面的查询确认。

`specificationOption: []` 表示清空全部选项；字段缺少或为 `null` 表示请求不完整，返回参数错误，不执行任何删除。这一区分必须落实到校验中。

### 8.3 为什么选择保留 ID

“先删除所有选项、再全部插入”更容易实现，但每次修改都会生成新选项 ID。本分析选择按 ID 处理增删改，更符合已有表单和实体结构。只有明确确认选项 ID 不需要保持、没有相关引用时，才考虑替换为全部删除后重建；不要在同一个接口中混用两种保存规则。

## 9. 删除规格

请求示例：`DELETE /specification/delete/26`。

成功响应：

```json
{ "code": 200, "message": "操作成功", "data": null }
```

处理步骤：

1. 校验 ID 为正整数，确认规格存在。
2. 检查是否被类型模板引用，存在引用时返回冲突，提示先解除模板关联。
3. 按 `spec_id` 删除该规格的全部选项。
4. 按主键删除规格主表记录。
5. 在同一事务内完成，失败时全部回滚。

注意：删除的是“规格与规格选项”，不是“商品和规格的关联信息”。不要把规格 ID 当作选项主键，应该使用 `WHERE spec_id = 当前规格ID` 删除选项。

### 9.1 当前项目已存在的引用问题

仓库 `shop.sql` 中，`tb_type_template.spec_ids` 存的是 JSON 文本，例如 `[{"id":27,"text":"网络"}]`。这意味着只删除两张规格表的记录可能留下模板引用。

本分析建议纳入基础删除规则：读取模板的 `spec_ids`，解析 JSON 数组，按其中的 `id` 精确判断是否引用目标规格；不要用 `LIKE '%27%'` 代替 ID 判断。对当前学习项目，可以先采用读取模板后解析的简单方案，无需先重构数据库。JSON 内容无法可靠解析时应报告关联数据异常，不能按“没有引用”继续删除。

这个检查与两表删除放在同一事务中，但当前设计没有跨模板编辑的并发协调，不能保证与另一个同时创建模板引用的请求完全互斥。并发完整性留待模板功能一起设计。

模板还存储规格名称 `text`。修改规格名称不会自动更新这些文本。本次修改接口只维护规格两表；后续模板显示应按 ID 取最新规格名称，或在模板功能中明确同步规则，避免把旧名称误认为同步成功。

`tb_goods_desc.specification_items` 和商品规格字段的实际消费、引用规则还需要在商品功能开发时确认。本分析的两表事务与模板检查不代表已覆盖所有商品引用，也不设计删除规格后重写商品或 SKU。

## 10. 各层职责与需要的数据库操作

### Controller

- 接收请求、触发参数校验、调用 Service、包装 `Result`。
- 不在 Controller 中操作两张表或处理选项差异。
- 校验或业务失败应转换为明确的错误响应；返回 `void` 的 Service 方法不等于无条件返回成功。

### Service

- 组织分页转换、详情组装、主子表新增、选项增删改、删除关联检查。
- 新增、修改、删除分别是一个事务边界。
- 不同时暴露含义相同的两个业务更新入口。对外保留一个“保存规格及选项”的修改方法，主表底层更新留给 Mapper。

### SpecificationMapper

- 条件查询主表列表。
- 按 ID 查询一条规格。
- 插入规格，并回填规格 ID。
- 按 ID 更新规格名称。
- 按 ID 删除规格。

### SpecificationOptionMapper

- 按 `spec_id` 查询全部选项并排序：这是编辑回显和修改比较的基础。
- 插入选项，可单条插入或批量插入；由 Service 保证集合不为空。
- 按 `id + spec_id` 更新一条选项的名称与排序。
- 按 `id + spec_id` 删除一条选项。
- 按 `spec_id` 删除这个规格的全部选项。

对于学习项目，Service 循环调用单条更新、删除就足够，不必通过分号拼接多条 UPDATE。批量更新不是完成业务正确性的前提。

模板引用检查需要模板 Mapper 提供模板关联数据读取能力；它不应放在规格选项 Mapper 中。

## 11. 当前实现中重写时应关注的点

以下依据当前源码观察，仅列出与本次设计直接相关的问题：

1. 新增缺少事务，选项插入失败时可能只留下规格主表。
2. 新增直接遍历选项集合，需要先区分合法空数组与非法 `null`，并跳过空集合插入。
3. 详情只查询主表，不能返回完整编辑表单，需要补按 `spec_id` 查询选项。
4. 修改只更新传入选项，缺少新增、移除选项处理，也缺少事务。
5. 当前选项修改 SQL 按 ID 更新，允许提交 `specId` 修改所属规格，需要明确限制选项归属。
6. 当前选项修改使用分号拼接多条 SQL，实际执行受连接和驱动配置影响，建议改为简单单条调用。
7. 业务 Service 同时存在 `updateSpecification` 与返回 0 的 `updateByPrimaryKey`，重写时只保留需要的业务入口。
8. 分页查询缺少固定排序；原始分页结果的总数应在转换列表前取得。
9. 当前删除已包含两表事务，但还未体现规格不存在、参数校验与模板引用阻止删除的规则。

## 12. 实现顺序与验收

建议先确定请求和响应对象，再按“详情 → 分页 → 新增 → 修改 → 删除”实现。详情能先帮助确认规格与选项的关联和排序，后续也能用它验证写入结果。

| 验收场景 | 预期结果 |
| --- | --- |
| 无条件分页、名称搜索、查询不到记录 | 总数正确，列表结构一致，排序稳定 |
| 非法页码、页大小、空白名称、重复选项名称 | 返回参数错误，无写入 |
| 新增带选项的规格 | 一条主表、多条选项，所有选项 `spec_id` 正确 |
| 新增空选项列表 | 主表成功，选项为空，无非法插入 SQL |
| 选项插入失败 | 新增主表一起回滚 |
| 查询详情 | 返回全部选项，按排序值及 ID 排序 |
| 修改时保留、改名、新增、删除同时发生 | 四种操作都正确，保留选项 ID 不变 |
| 选项 ID 属于其他规格、不存在或重复 | 整次修改被拒绝，原数据不变 |
| 修改提交空数组 | 当前规格全部选项删除，规格保留 |
| 修改缺少列表或列表为 null | 拒绝请求，已有选项不被删除 |
| 重复保存相同表单 | 成功，已有选项 ID 不变 |
| 修改中任一步失败 | 规格名称、选项变化全部回滚 |
| 删除未被引用的规格 | 主表和选项一起删除，其他规格不受影响 |
| 删除已被模板引用的规格 | 返回冲突，主表和选项保留 |
| 删除不存在的规格、查询不存在的规格 | 返回规格不存在 |
| 删除主表失败 | 前面删除的选项回滚 |

这些是后续实现的验收标准，本次只拟定分析文档，未执行接口或数据库测试。
